# v0.8.2 — Cuestionario reordenado + matriz profunda + pantalla de carga MVP

> Estado: 🟢 Done (implementada; `cargo test` 159/159 OK, 3 ignorados; `cargo clippy --all-targets` 0 warnings).

## Objetivo
El cuestionario pregunta en el orden correcto (primero **qué** se construye, después **cómo**), profundiza por subtipo (un lenguaje no es un OS, un plugin no es un motor), trata open-source como rama transversal y, al terminar, genera en una **pantalla de carga** el CONTEXT completo + la serie de versiones hasta el MVP, sin pasar por el chat.

## Alcance (concreto)

### A. Reorden: Cat/Tipo primero + genéricas contextualizadas
Nuevo orden: `Nivel → Cat → Tipo → 4 genéricas → familia → OSS → IA`.
Antes se pedían las funcionalidades sin saber qué tipo era; ahora `nombre/descripción/objetivo/funcionalidades` mantienen sus ids (misma validación y plantillas) pero cambian título/hint por familia (`generic_questions`: en Servicio sugiere endpoints, en Sistema distingue lenguaje/OS, etc.).
El paso `nombre` se **omite** cuando ya viene de la pantalla de inicio (`Answers.nombre_locked`, fijado al crear/abrir): el wizard no vuelve a preguntar lo ya ingresado; la cabecera muestra el nombre del proyecto.

### B. Matriz profunda por subtipo (`levels.rs`)
* **Sistema:** `LenguajeRuntime` pide `sintaxis + toolchain + arch + compat`; `OsDistro/KernelModulo/ContenedorVm` piden `arch + arranque + syscalls/ABI + compat`; `DriverFirmware/Utilidad` lo anterior sin syscalls.
* **Librería:** `PluginExtension` añade `host_api` (dónde se instala); `MotorEngine` añade `ui_ux + estilo + plataformas`; `Framework/Starter` la base.
* **Nuevos campos** (`Answers`): `sintaxis, toolchain, syscalls, host_api` (+ `oss_repo, oss_gobierno, oss_contrib`).

### C. Rama transversal open-source
`is_oss(cat, fact, lic)`: App/Servicio con facturación `Código abierto`, o resto con licencia distinta de `Uso interno`. Bloque final siempre visible (3 áreas cortas, nunca bloquean): `oss_repo + oss_gobierno + oss_contrib`. `SPECS.md` suma `## Open source` solo si aplica; `gaps()` lo incluye si falta.

### D. CONTEXT engordado (se mantiene 3+plan, sin fusionar)
* `PROJECT.md` suma `## Tipo de sistema` + `## Gaps`.
* `SPECS.md`: Stack/Plataforma siempre renderizados (con gap explícito si vacío); secciones por subtipo; criterios por funcionalidad (existentes) intactos.
* Cero placeholders mudos: `or_dash` devuelve `Pendiente de definir: completar en Plan/MVP.` (antes `(sin detallar)`).

### E. Pantalla de carga MVP (sin chat)
* Nuevo `View::Generating` (`views/questionnaire.rs::view_generating`): fase + barra + nota + `Detener` (`GenCancel`).
* `Finish` guarda la base (`PROJECT/SPECS/CONTEXT` + layout) y, con API, entra a `Generating` y dispara **una sola llamada** con el system especial `mvp_prompt` (convenciones + resumen + gaps + serie). La respuesta se trocea por `---FILE: <ruta>---` (`parse_mvp_files`) y `write_mvp_docs` escribe los 7 archivos con validación por versión (lo ausente/inválido cae al fallback determinista con aviso en el Log).
* **Serie fija** (`mvp_versions`): `v0.1 Base funcional → v0.2 Núcleo usable → v0.3 Integración y calidad → v1.0 MVP` + `ROADMAP + VERSIONS + ToDo` por serie.
* Sin API: serie determinista offline directa al Chat (aviso visible). `GenCancel` invalida por generación (`gen_run`) y vuelve al paso IA para reintentar. Al cerrar: chat `Plan inicial` en modo Plan con resumen corto (sin prompt gigante ni turno en curso).
* Retirado: `begin_plan_turn_auto` + turno Plan automático en el chat (el `plan_auto` legacy de `PlanDone` queda como red de seguridad sin emisores).
