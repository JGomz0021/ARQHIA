# v0.9.3 — MCP mínimo (stdio + HTTP, tools)

## Objetivo
Integrar servidores **MCP** (Model Context Protocol) como fuente de tools del agente: stdio + HTTP, solo métodos `tools/*`, con la política de permisos existente. Lo avanzado (pestaña, resources/prompts, marketplace) es v1.0.1. **Bloquea v1.0**: el release estable lo incluye y lo prueba.

## Alcance (concreto)

### A. Config (`config.rs`, sección `[mcp]`)
```toml
[mcp.servers.mi-docs]
transport = "stdio"                  # o "http"
command = "mi-docs-mcp"              # binario ya instalado
args = ["--port", "8080"]
url = "http://localhost:8000/mcp"    # solo si transport = "http"
auto = false                         # true = sin pedir permiso por llamada
timeout_s = 30
```
*   Comando resuelto por `PATH` y registrado en el Log al conectar.
*   `npx`/`uvx`/`npm`/`pip`/`curl` como comando → categoría `Install`: pide aprobación (coherente con `POLICIES.md` §1). Solo binarios instalados van en automático.

### B. Protocolo (`src/mcp.rs`, nuevo, sin crates nuevos)
*   stdio: spawn del proceso, `initialize` + `tools/list` al abrir el turno (cache 5 min), `tools/call` por llamada, kill al cerrar.
*   HTTP: Streamable HTTP POST con `Accept: application/json, text/event-stream` (request/response por llamada, sin SSE persistente).
*   Solo `tools/*`. `resources/*` y `prompts/*` → error claro "hasta v1.0.1".
*   JSON-RPC a mano sobre `tokio`/`reqwest` ya existentes.

### C. Integración agente (sin tocar el loop v0.9.1)
*   `tools::execute()` enruta `mcp__{servidor}__{tool}` al cliente MCP; schemas anexados a la lista nativa con descripción `[MCP mi-docs]`.
*   `category_of_call`: MCP → `ToolCat::Net`, salvo `auto=true` del servidor (entonces `Read`, automático). El modal de aprobación existente las cubre sin cambios.
*   Las tools MCP no tocan disco directamente; la aprobación es la protección (el guard de workspace no aplica a sus args).

## Tareas técnicas
*   Archivos nuevos: `src/mcp.rs`.
*   Modifica: `config.rs` (`McpConfig`), `agent/tools.rs` (enrutado + schemas + categoría), `app/state.rs` (cache de clientes por turno).
*   Sin crates nuevos. Sin migración DB. Sin cambios al loop auditor/fix.

## Criterio Done (estricto)
*   Servidor stdio stub: `tools/list` visible y `tools/call` ejecuta con aprobación (con `auto=false` pide; con `auto=true` no).
*   Servidor HTTP stub: mismo flujo por POST.
*   `command = "npx ..."` → pide aprobación Install antes de arrancar.
*   Servidor caído/timeout → error parcial en el Log, el turno sigue.
*   Schemas > 4 KB se truncan con aviso (no se traga el contexto).

## Test de Funcionalidad
1.  Stub stdio con tool `echo`: pedir "usa echo de MCP" → modal → resultado visible.
2.  Mismo stub con `auto=true` → sin modal.
3.  Stub HTTP apagado → error claro + turno continúa.
4.  `command = "npx algo"` → pide Install; denegar no arranca nada.

## Riesgos
*   Servidores colgados → `timeout_s` + kill; nunca bloquear el turno.
*   Schemas gigantes → tope 4 KB con aviso.
*   npx como instalación silenciosa → bloqueado por defecto (Install).

## Dependencias
v0.9.2 (skills; sin interacción) + v0.9.1 (roles; el worker consume MCP como una tool más). Bloquea v1.0.
