# v0.8 — Cuestionario rediseñado + estructura de proyecto + onboarding de API

## Objetivo
Rediseñar el cuestionario para que sea **genérico + por nivel + con preguntas
opcionales generadas por IA**, y que su salida no sea un solo archivo sino el
**esqueleto documental completo del proyecto** (`PROJECT.md`, `SPECS.md`,
`CONTEXT.md`) más la **estructura de carpetas**. Añadir además el **onboarding
de primer arranque** que pide configurar una API. Sustituye el enfoque de
preguntas fijas de v0.5 (`ESPEC.md`).

## Alcance (concreto)

### A. Cuestionario

**Paso 0 — Nivel** (`pick_list([Principiante, Intermedio, Avanzado])`). Guarda
`level: Level`. Cambiar de nivel pregunta si se descartan respuestas.

**Bloque genérico (siempre, 4 pasos):**
1.  `nombre`: texto 1 línea, obligatorio, máx 60.
2.  `descripcion`: multilínea, obligatorio, mín 10 chars.
3.  `objetivo`: multilínea, obligatorio, mín 10 chars.
4.  `funcionalidades`: multilínea, obligatorio (una por línea / bullets).

**Bloque por nivel:**

*   **Principiante (diseño y decisiones, no código):**
    *   `estilo_visual`: texto ("describe el look & feel / referencias").
    *   `plataforma`: múltiple `{multiplataforma, web, nativa, juego}`.
    *   `facturacion`: múltiple `{suscripciones, pago-unico, api, uso-personal}`.
*   **Intermedio:**
    *   `ui_ux`: texto.
    *   `plataforma`: múltiple `{multiplataforma, web, nativa, juego}`.
    *   `stack`: múltiple/opcional `{Rust, Python, JS/TS, Otro}` + texto libre
        (vacío permitido = "a decidir").
    *   `facturacion`: múltiple `{suscripciones, pago-unico, api, uso-personal}`.
*   **Avanzado:**
    *   `ui_ux`: texto.
    *   `plataforma`: múltiple `{multiplataforma, web, nativa, juego}`.
    *   `stack`: múltiple/texto (o "no especificado").
    *   `arquitectura`: texto ("módulos, capas, escalado").
    *   `facturacion`: múltiple `{suscripciones, pago-unico, api, uso-personal}`.

**Bloque IA opcional (saltable):**
*   Botón `Generar preguntas adicionales (IA)` tras el bloque por nivel.
*   Usa el **provider activo** para proponer **3–5 preguntas** adaptadas a lo
    respondido. El usuario responde o pulsa `Saltar`.
*   Si **no hay provider configurado**, el paso se muestra deshabilitado con
    aviso y enlace a Configuración; el flujo continúa y genera los docs igual.
*   Envía al LLM las respuestas del cuestionario: se rige por `POLICIES.md` §2
    (privacidad) con aviso visible.

**Validación** por paso (no avanzar con genéricos vacíos o múltiples sin
selección del nivel correspondiente). Wizard con `Atrás`/`Siguiente` y
`progress_bar` + `Nivel: X — Paso Y/Z`.

### B. Estructura del proyecto generado

Al finalizar el cuestionario se crea/asegura:

```
{workspace}/
├── Project/                 # código + git del proyecto del usuario
│   └── (vacío al inicio)
├── ToDo.md                  # tablero de ejecución (lo mantiene el agente)
└── CONTEXT/                 # SSOT del proyecto generado
    ├── CONTEXT.md           # índice + estado vivo + siguiente paso (entrada del agente)
    ├── PROJECT.md           # visión, objetivo, alcance, usuario
    ├── SPECS.md             # especificación funcional (reemplaza ESPEC.md)
    ├── ROADMAP.md           # versiones de alto nivel
    ├── VERSIONS.md          # índice de estado por versión
    └── VERSIONS/
        └── v0.1.md          # se genera en la primera ejecución de Plan
```

*   **`Project/` es la raíz de código/git.** El workspace de v0.3 pasa a
    estructurarse así; el guard del agente permite escribir en `Project/`,
    `CONTEXT/` y `ToDo.md`, y sigue bloqueando fuera del workspace.
*   **`CONTEXT.md` es índice + estado vivo**, no un volcado: resume situación
    actual y siguiente paso (rol que en el producto cumple `HECHO.md`), y evita
    duplicar `PROJECT/SPECS/VERSIONS`.
*   **`ROADMAP.md`, `VERSIONS.md` y `VERSIONS/v0.1.md`** se generan al ejecutar
    el primer **Plan** (modo v0.7.1). Si hay provider, el cuestionario puede
    ofrecer generarlos también vía IA inmediatamente.
*   **Migración:** si existe `CONTEXT/ESPEC.md` (v0.5), se renombra/copia a
    `SPECS.md` y se conserva un `ESPEC.md` legacy con nota.

### C. Onboarding de primer arranque (API)

*   Si **no hay ningún provider configurado** al arrancar, Home muestra un
    mensaje de bienvenida que invita a configurar una API:
    `Elegir provider + pegar API key (+ model/base_url)` con botón `Guardar` y
    `Configurar después`.
*   Reutiliza la pantalla Config → API (pick_list, validación de key, probar
    conexión). No es un modal bloqueante: la app se puede usar para exportar/
    configurar antes.
*   Al guardar la primera API, el aviso desaparece y no vuelve a mostrarse.

### D. Documentos generados (plantillas minijinja)

*   `PROJECT.md`: nombre, descripción, objetivo, usuario/público, alcance
    (según nivel).
*   `SPECS.md`: funcionalidades + UI/UX + plataforma + stack (si procede) +
    arquitectura (según nivel) + facturación. Secciones por nivel:
    *   Principiante → `## Estilo visual`, `## Plataforma`, `## Facturación`.
    *   Intermedio → `## UI/UX`, `## Plataforma`, `## Stack`, `## Facturación`.
    *   Avanzado → `## UI/UX`, `## Plataforma`, `## Stack`, `## Arquitectura`,
        `## Facturación`.
*   `CONTEXT.md`: índice de `CONTEXT/` + estado "Proyecto recién definido" +
    siguiente paso "Ejecutar Plan".

### E. Sesiones de chat por provider (id estable)

Cada chat mantiene un **`session_id` estable** para que el proveedor detecte la
conversación y mejore caché de prompt, coste y trazabilidad (v0.8).

*   **Persistencia:** `chats.session_id TEXT` (migración idempotente; NULL en
    chats viejos). Se genera (UUID corto / `nanoid`) la primera vez que el chat
    envía un turno; se conserva al archivar/mover/enviar.
*   **Envío por provider** (campo de body o header según soporte):
    *   **OpenRouter:** `session_id` en el body.
    *   **OpenAI y OpenAI-compatible (Groq…):** `prompt_cache_key`; si el
        endpoint no lo acepta, fallback a `user`.
    *   **Anthropic:** header `x-session-id` (trazabilidad; la caché real usa
        `cache_control`, backlog).
    *   **Local (LM Studio):** sin efecto.
*   **API:** helper `llm::session_body_fields(provider, &session_id)` que
    devuelve los pares a inyectar, para no duplicar lógica en cada provider.
    El id se pasa desde `start_turn`/`send_plain_chat` (una vez por chat).
*   **UI:** acción `Reiniciar sesión` en el menú `⋯` del chat (regenera el id y
    limpia la caché de ese chat); el id no se muestra salvo tooltip.
*   **Sin provider con sesiones:** el id se guarda igual y el flujo no cambia.

## Riesgos
*   Wizard dinámico → tests unitarios por nivel + e2e manual de los 3.
*   Coste/privacidad del bloque IA → aviso + saltable + usa provider activo.
*   Cambio de guard `Project/` puede romper v0.3–v0.7 → migración y tests de
    escritura dentro/fuera.
*   Crear `ROADMAP/VERSIONS` vía IA puede desviarse → por defecto se generan en
    Plan; la vía IA es opcional.
